# Validation of the sim's machine figures against published baselines

Validation notes. All sources were read on **2026-11-20**. Statements marked **Verified** come straight from the linked source. Statements marked **Inference** are reasoning that has not been tested. Figures marked **Derived** are hand arithmetic on the code's constants, not a sim run. Nothing here is a run of the twin, and no number in these notes describes a customer's plant.

---

## 1. The problem

The weakness raised against AdaTwin is: "No validation against real data or a published baseline." It holds today. The simulation (`packages/sim`) is deterministic and tested for its own logic, but no machine figure it runs on has been checked against a measured or published value.

What makes this sharper for the five sample plants:

- **The sample plants open with no machine figures at all.** `sampleMachines()` in `apps/frontend/src/twin/sample.ts` gives each machine an id, name, count and, for auxiliary machines, the auxiliary flag. Nothing else. Every station figure then falls back to the same hard-coded value, marked **Assumed** in the twin step (`stationParam()` and `STATION_PARAMS` in `apps/frontend/src/twin/project.ts`).
- **The research path is closed for them until the user adds details.** "Find its parameters" is disabled while a machine has no document and no manufacturer and model (`needsInfo()` in `packages/agent/src/machines.ts`; `infoMissing` in `apps/frontend/src/pages/steps/twin.tsx`). The sample machines have neither.
- **When research does run, the figures are AI-drafted at runtime, not fixed in code.** `fillParameters()` (`packages/agent/src/fill-parameters.ts`) asks the document-reader agent first, then the web-researcher agent (Gemini with search), then falls back to the same assumed values. So no range of "what the agents would draft" can be stated from the code: it depends on the documents, the model and the search results of that run.

So the honest comparison for the sample plants is between the **hard-coded fallbacks** and published figures. That is what these notes do.

## 2. What the sim uses per machine

From `packages/sim/src/graph.ts`, `kernel.ts`, `random.ts`, `capacity.ts` and `scenario.ts` (**Verified** by reading the code):

| Parameter            | Meaning in the sim                                                     | How the kernel uses it                                                                                                              | Sample-plant value (fallback)        |
| -------------------- | ---------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------ |
| `units`              | Identical machines side by side                                        | One unit per count; each fails and is repaired on its own                                                                           | Count from `sample.ts` (user input)  |
| `cycleTime`          | Mean seconds for one unit to process one unit of work                  | Log-normal draw per unit of work                                                                                                    | 120 s                                |
| `cycleTimeVariation` | Standard deviation / mean of the cycle time                            | Log-normal with that coefficient of variation                                                                                       | 0.25                                 |
| `mtbf`               | Mean seconds of **working** time between failures                      | Weibull with shape 2 ("unlikely soon after service, likelier with age"); wear accrues only while the unit works                     | 14,400 s (4 h)                       |
| `mttr`               | Mean seconds to repair **once a crew starts**                          | Exponential draw; repairs wait for a free maintenance crew (1 by default); preventive service takes 25% of MTTR                     | 1,200 s (20 min)                     |
| `scrapRate`          | Share of finished units of work scrapped                               | Bernoulli per unit of work                                                                                                          | 0.01                                 |
| `spares`             | Auxiliary machines only: standby units                                 | The auxiliary machine keeps supplying while no more than `spares` units are down                                                    | None                                 |

Auxiliary machines (gas valve trains, overhead cranes) use only `mtbf` and `mttr`. While any unit of one is down (beyond its spares), every station or source that needs it stops. Which machines need which auxiliary machine is drafted by the flow-drafter agent from the panorama and process text, then corrected by the user. It is not fixed in code.

**Uptime.** `shiftCapacity()` uses uptime = MTBF / (MTBF + MTTR). For the fallbacks this is 14,400 / 15,600 = **0.923** (**Derived**).

**Scenario effects.** `applyScenario()` cuts MTBF by 2% per °C above 25 °C (floor 40% of nominal) and lengthens cycle time by 0.5% per °C. The code calls these "modelling assumptions, shown to the user, not measurements". No published source for either factor was found (see section 6). Under the default scenario "Hot week, full order book" (34 °C), the fallback MTBF becomes 3.28 h, cycle time 125.4 s, and uptime **0.908** (**Derived**).

**Provenance.** Every value carries where it came from (`Provenance` in `graph.ts`): `doc` (document name and page), `web` (URL, quoted passage, and `datasheet` or `typical` confidence), `assumed` (fallback), or `user` (typed in, or a change the user picked).

## 3. Method

For each machine:

1. **Map it to an equipment class** that published reliability data covers (for example Feed pumps → boiler feedwater centrifugal pump).
2. **List what the sim uses** for it and where each value comes from today.
3. **Find a published baseline** for MTBF or failure rate, MTTR, availability and cycle or throughput, from a high-trust primary or standard source, and record the range across the relevant sub-classes.
4. **Put both on the same basis** before comparing:
   - **Time basis.** The sim's MTBF counts working time only. The main source used here, TM 5-698-5, computes MTBF over calendar time ("Tp (total period): The calendar time over which data for the item was collected"). If failures happen only while running, operating-basis MTBF = calendar MTBF × the share of calendar hours the machine runs. To keep the comparison conservative, each machine note also shows the published figure scaled by one illustrative duty: one 8-hour shift, 5 days a week, 52 weeks = 2,080 of 8,760 hours (0.237). This is **Derived**; the true duty of the surveyed fleets is not published.
   - **Repair basis.** TM 5-698-5's MTTR is repair downtime "excluding logistics delay time". The sim's MTTR is "mean seconds to repair once a crew starts", so it also excludes waiting. The two are comparable. Mean down time (MDT) in the source includes logistics delay and is not compared with MTTR.
   - **Availability basis.** TM 5-698-5's inherent availability is Ai = MTBF / (MTBF + MTTR), the same formula as the sim's uptime. Its operational availability (Ao) also counts preventive maintenance and logistics delay.
5. **Give a status**:
   - **within range**: the sim value lies inside the published range after the basis conversion.
   - **outside range**: it lies outside, even after the most favourable plausible basis conversion.
   - **not yet comparable**: no verified published figure exists for that class and parameter, or the sim's unit of work has no physical definition the source could be compared with.
6. **Write a validation plan**: the data that would settle it, the test, and an acceptance criterion. The acceptance criteria are proposals for the team to adopt, not results.

**Cycle time is "not yet comparable" for every machine.** The unit of work in a sample plant is a plant-chosen count ("batches", "parts", "castings", "motors") with no defined size, mass or operation content. No published cycle time can be set against 120 s per "batch" until the unit of work is defined. The same holds for `cycleTimeVariation` and `scrapRate`: no verified class-level source was found.

Sources named in the brief that were **not used for numbers**:

- **IEEE Std 493-2007 (Gold Book).** Paywalled. IEEE SA lists IEEE 3006.8-2018 (published 2018-10-17), which "describes data supporting the reliability evaluation of existing" industrial and commercial power systems, as an Active Standard (S7). - **OREDA 6th edition (2015).** Paywalled (S6). No OREDA figure appears here.
- **NERC GADS.** Covers utility generating units (S8). An ISO New England summary of GADS class averages was downloaded, but its extracted table could not be read reliably, so no GADS figure appears here. A utility steam unit is also not the same class as a boiler-room boiler.
- **NUREG/CR-6928 and the INL component performance studies** (pump fail-to-run rates). The NRC and INL servers refused automated access (HTTP 403), so no figure appears here.
- **NSWC-11 mechanical reliability handbook (May 2011)**, **MIL-HDBK-217F**, **MIL-HDBK-338B**, **CCPS process equipment reliability data**. Not consulted. NSWC-11 and MIL-HDBK-217F are prediction methods built up from parts, not field baselines. TM 5-698-5 cites MIL-HDBK-338B section 8.3.2.5.2 for its zero-failure estimates (marked * in S1).
- **DOE / ASME boiler efficiency references.** The sim has no efficiency parameter, so they have nothing to be compared with.

**Caveat on S1, in its own words:** "The actual values that can be predicted for a specific system from the use of this data are not necessarily the actual results that the facility may encounter. The value of using the data is to establish a baseline for the facility to use as a comparison." Its surveyed facilities include "office buildings, hospitals, water treatment facilities, power generation plants, utilities, manufacturing facilities".

**Reading the table.** Wherever a verified baseline exists, the fallback MTBF is between about 500 and about 450,000 times shorter than the published figure (CNC machine tools at the low end, valve operators at the high end), and the fallback MTTR is between about 4 and about 150 times shorter (control panels to boilers). Even after scaling S1 to one shift a day, every published MTBF stays at least about 500 times the fallback. The two errors partly cancel in the uptime ratio, which is why the sample plants' uptime (0.923) looks plausible next to a CNC machine tool (S2) while being far below every S1 class. The practical effect (**Inference**): a sample twin sees about two failures per machine-unit per shift (8 h / 4 h; about 2.4 at 34 °C), each short, where the published classes would see one failure per unit in months to centuries of running, each lasting hours to days. Failure-driven changes (faster repairs, an extra maintenance crew, spares on auxiliary machines) are therefore measured against a failure pattern no published source supports.

## 6. Gaps that remain

1. **No real-plant data has been compared with any run.** Every comparison here is parameter against published summary. None is model output against a measured shift.
2. **The sample plants run on placeholders.** Until a sample opens with researched figures, or the fallbacks are replaced by class-specific defaults with a cited source, the sample plants cannot be called validated.
3. **AI-drafted figures are not checked.** `researchOnWeb()` keeps any value with a parseable URL. Nothing checks the value against the quoted passage, against a class range, or for time basis (calendar vs operating).
4. **Time basis is not recorded.** `Provenance` has no field for calendar-time vs operating-time MTBF, so a researched calendar MTBF is used as working-time MTBF without conversion.
5. **Cycle time has no physical anchor.** Units of work have no defined size, so no published cycle time or throughput can be compared.
6. **The failure distribution is assumed.** The kernel draws working time to failure from a Weibull with shape 2 (rising hazard) and repair time from an exponential. The only verified field fit found (S2, CNC turning centres) reports a Weibull shape near 1 and states that "failure and repair rates are nearly constant". That supports the exponential repair time and contradicts the shape-2 wear-out, for that class. No verified fit was found for the other classes.
7. **Heat factors are unsourced.** The 2% MTBF loss and 0.5% cycle-time gain per °C above 25 °C are "not found in a verified source". The code already labels them as modelling assumptions.
8. **Classes with no verified baseline:** cutting tables, welding bays (reliability), grinding station, inspection bench, rewinding workbenches, overhead cranes (reliability).
9. **Crane capacity is not modelled.** An auxiliary machine has no throughput, only failures. CMAA 70 Class D cranes, the class for foundries and heavy machine shops, are specified for 10 to 20 lifts per hour (S4). The plant-sized default demand is about 240 units of work per 8-hour shift (**Derived**, see the plant notes), about 30 per hour. If every unit of work needs one crane lift, a Class D crane could not keep up (**Inference**). The sim would not show it.
10. **Paywalled standards not read:** OREDA, IEEE 493 / 3006.8, CCPS. They are the natural next sources for pumps, valves and electrical equipment.
11. **S1 is old and facility-oriented.** Data from 2006 and earlier, largely HVAC and power plant rooms. It is the best public, primary, numeric source found, not a perfect class match.

## 7. Real-data candidates

| Candidate                                                                                                                         | What it is                                                                                                            | Fits                                     | Use                                                                                                    |
| --------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------- | ---------------------------------------- | ------------------------------------------------------------------------------------------------------ |
| **A plant's own maintenance and production records** (work orders with failure and return-to-service times; shift output counts) | Real data for the plant the twin is of                                                                                | Every machine                            | The only source that can validate a twin end to end. The document-reader agent already reads maintenance records attached to a machine. |
| **S1 Appendix B** (TM 5-698-5)                                                                                                    | Fleet summaries: unit-years, failures, MTBF, MTTR, Ai, Ao                                                             | Pumps, boilers, panels, MG sets, valves  | Parameter-range checks and class-specific defaults                                                     |
| **Bearings (IMS, University of Cincinnati)** and **FEMTO Bearing** (S9)                                                         | Real run-to-failure and accelerated-life bearing tests                                                                | Pumps, motors, MG sets (bearing wear)    | Test the Weibull shape-2 wear-out assumption on one failure mode                                        |
| **Milling** (S9) and **CNC Milling Machine, 2010 PHM Society Data Competition** (S9)                                              | Real milling-insert wear and cutter remaining-life measurements                                                        | Milling machines, boring mill            | Tool-wear as a cause of stoppage; cutting-time distributions                                           |
| **Turbofan Engine Degradation Simulation (C-MAPSS)** (S9)                                                                         | Simulated, not measured: "Engine degradation simulation was carried out using the Commercial Modular Aero-Propulsion System Simulation" | None of the sample classes   | Only a benchmark for wear-out modelling methods. Not real data.                                        |
| **AI4I 2020** (S10)                                                                                                               | Synthetic                                                                                                             | None                                     | Not real data; not recommended                                                                         |

**Most useful for a first real-data validation run (Inference):** a plant's own work-order history for one machine class, paired with S1 Appendix B as the published range. Of the public datasets, the IMS and FEMTO bearing sets are the most useful, because they test the kernel's wear-out assumption with measured run-to-failure data. The machine figures themselves (MTBF, MTTR) have to come from the plant's own records.
